# Release Discipline

## 目标

这份文档定义 `action-guard` 从源码仓库走向对外版本发布时，最低需要遵守的发布纪律。

当前项目仍处于 `early preview`，所以这里强调的是：

- 每次发布都要让接入方知道“哪些是稳定边界”
- 每次发布都要让维护方自己知道“这次到底改了什么”
- 不把兼容性风险混在普通增强里一起模糊发布

## 当前版本节奏建议

当前建议按以下语义区分版本：

- `0.1.x`：early preview 阶段，允许增强较快演进，但仍要尽量保护主链路契约
- `0.2.x`：准备进入更稳定的接入期，减少默认行为波动
- `1.0.0`：只有在主链路、文档、治理、观测、发布流程都足够稳定时再考虑

## 每次发布前的最小检查

至少确认以下内容：

1. `mvn test` 可以通过
2. `bash scripts/run-demo-smoke.sh` 可以通过
3. README、Quick Start、Starter Config、FAQ 已同步到当前行为
4. Kafka、Redis、ops-web 等非主链路模块的当前状态描述没有误导
5. 默认配置变化、SPI 变化、schema 变化已经被记录

## 变更分类

发布说明建议至少把变更分成三类：

### 1. 兼容增强

例如：

- 新增文档
- 新增可选配置
- 新增能力模块
- 新增指标或告警事件

### 2. 受控变化

例如：

- 默认值调整
- demo 行为调整
- 主链路推荐接入方式更新

这类变化需要在 release note 中明确写出。

### 3. 破坏性变化

例如：

- `ActionPublisher` / `ActionStepHandler` / `ActionMetricsRecorder` 等公开 API / SPI 变化
- YAML 定义字段语义变化
- 状态机关键语义变化
- schema 不兼容调整

这类变化不应悄悄混进普通版本说明里，必须显式写出迁移影响。

## Release Note 最低结构

每次对外版本建议至少包含：

- **Summary**：这次发布的目标
- **Highlights**：最重要的 2-5 个变化
- **Compatibility Notes**：兼容性说明
- **Migration Notes**：如果有默认行为变化或破坏性变化
- **Verification**：本次发布实际执行过哪些验证

## BOM 与模块发布

如果对外发布模块版本，建议：

- 同步发布 parent 与 `action-guard-bom`
- 保持推荐主路径模块版本一致
- 不要让接入方自己拼核心模块版本组合

## 当前推荐姿态

在正式进入稳定版本前，更合适的对外表述是：

- 可公开评审
- 可试用
- 主链路可验证
- 非所有模块都已达到稳定生产承诺
