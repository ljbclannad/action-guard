# 公开发布准备

## 目标

这份文档用于回答一个具体问题：

`action-guard` 在什么条件下，可以从 private 仓库切换到 public 仓库。

这里关注的不是“功能是不是已经做完”，而是“对外公开后，陌生使用者是否能理解、运行、协作，并且不会暴露不该暴露的内容”。

## 当前判断

以当前仓库状态看，项目已经接近“可公开预览”的水平，但更适合按“公开可评审 / 非稳定生产承诺”来管理预期，而不是直接宣称成熟可用。

原因：

- 最小主链路和治理主路径已经存在
- 基础文档、示例、License、Contributing 已补齐
- 仍有部分非主链路模块处于弱承诺状态，例如 Kafka、Redis 扩展能力

因此切 public 前，建议先通过下面这份检查清单。

## 推荐执行清单

切换 public 前，建议按下面顺序执行，并逐项勾验：

1. 检查 `.gitignore` 与工作区，确认私有开发辅助文件未进入提交面
2. 运行一次最小测试或定向测试，确认仓库不是失效状态
3. 运行 demo 冒烟脚本，确认陌生开发者能跑通最小链路
4. 检查 README、快速开始、FAQ、模块选择建议 是否与当前实现一致
5. 明确 README 中的成熟度表述，例如“early preview”
6. 检查非主链路模块声明是否清晰，例如 Kafka、Redis、ops-web
7. 最后再切换仓库可见性，并补充 issue / PR 基础模板
8. 检查 CI、SECURITY.md 和 release discipline 是否已经补齐

## 必须满足的条件

### 1. 发布面安全

必须确认以下内容不会进入公开发布面：

- `docs/CLAUDE.local.md`
- `docs/superpowers/`
- `docs/plans/`
- 任何只服务于本地开发习惯、内部代理流程、私人账号或私有基础设施的信息

当前仓库已经通过 `.gitignore` 对上述路径做隔离，但在切 public 前仍应再做一次人工检查。

### 2. 文档可读性

公开读者至少要能回答以下问题：

- 这个项目解决什么问题
- 最小依赖组合是什么
- 怎么跑通 demo
- 当前官方推荐主路径是什么
- 哪些模块是稳定主路径，哪些只是占位或弱承诺能力

最低要求对应文档：

- `README.md`
- `docs/quick-start.md`
- `docs/module-selection.md`
- `docs/faq.md`
- `docs/compatibility-and-versioning.md`

### 3. 示例可运行

至少要保证一个默认示例可以被陌生开发者按文档运行：

- `examples/action-guard-demo`
- `scripts/run-demo-smoke.sh`

切 public 前，应该以全新视角验证一次：

- 配置是否自洽
- 依赖说明是否齐全
- 失败时是否能从日志或文档定位问题

### 4. 模块承诺清晰

公开仓库不怕能力不全，怕的是承诺不清。

切 public 前需要明确：

- RabbitMQ 是当前默认主路径
- Kafka 在第一版仅占位保留，不是默认推荐接入组合
- H2 file 主要用于本地演示，生产建议切 MySQL
- `ops-web` 仍是应用壳，治理主能力当前在 `ops-api`

如果某个模块仍在占位或薄适配阶段，README 和相关文档里必须显式说明。

### 5. 开源协作基本面

至少需要具备：

- `LICENSE`
- `CONTRIBUTING.md`
- `SECURITY.md`
- 清晰的 issue / PR 预期
- 可理解的模块结构和命名

如果外部贡献者无法判断往哪里提改动、如何验证改动，public 只会增加维护噪音。

### 6. 最小质量基线

切 public 前至少要确认：

- 根项目可以完成一次测试或最小验证
- demo 冒烟脚本可执行
- 关键核心模块存在基础单测或系统测试覆盖

这里不要求“所有能力都生产级”，但要求仓库不是“只能看不能跑”的展示代码。

建议至少执行以下命令中的一组：

```bash
mvn test
```

或：

```bash
bash scripts/run-demo-smoke.sh
```

## 建议满足的条件

这些不是硬门槛，但满足后会明显降低公开后的沟通成本：

- README 明确版本状态，例如“early preview”或“milestone prototype”
- 补一份发布节奏说明，例如 alpha / beta 阶段的兼容性预期
- 为后续 public 维护准备 issue template 和 PR template
- 补基础 CI 工作流
- 在 `docs/faq.md` 中明确当前不支持或不承诺的能力

## 不建议在切 public 时做的事

为了尽快公开，不建议把以下动作和“切 public”绑定成同一批工作：

- 一次性补齐所有 Kafka 能力
- 一次性做整仓双语翻译
- 在还没稳定前就承诺复杂工作流、并行分支或全平台适配

更合理的方式是：

- 先公开最小主路径和已完成治理能力
- 用文档明确边界和非目标
- 再逐步补能力模块和外部协作流程

## 建议的切换结论

如果以下三件事都成立，就可以考虑把仓库从 private 切到 public：

1. 私有开发约束文件和内部辅助文档确认未进入发布面
2. README、快速开始、FAQ、模块说明能支撑陌生开发者跑通最小链路
3. 仓库对“当前推荐主路径”和“非稳定模块”做了明确声明

在这个前提下，public 的建议姿态是：

- 把项目标记为“可公开评审、可试用”
- 不把当前阶段表述为完全稳定的生产承诺
- 通过持续补文档、测试和模块承诺，逐步提升公开成熟度

## 切换前最终检查表

- [ ] 工作区内没有要暴露的本地开发约束文件
- [ ] README 与 docs 导航不包含内部计划文档
- [ ] Kafka、Redis、ops-web 的当前承诺已经写清楚
- [ ] 至少一组测试或 demo 冒烟已成功执行
- [ ] License、Contributing、Quick Start、FAQ 已同步到最新状态
- [ ] 仓库首页对成熟度预期表述清晰
- [ ] CI、SECURITY.md、release discipline 已准备完成
